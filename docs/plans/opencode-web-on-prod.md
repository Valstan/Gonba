# OpenCode Web на прод-боксе (анонимный пул, доступ из браузера)

> План-ранбук, 17.10.2026. Запрос владельца: «поставить опенкод на прод и управлять им
> удалённо из браузера с любого компьютера; аккаунт анонимный — без ключа».
> Схема пулов взята у Мозга: плейбук `brain_matrica/docs/plans/opencode-two-pools-deploy.md`
> (два пула лимитов), грабли — [G460](../../../brain_matrica/cross-project-ideas/gotchas/G460.md)
> (пароль/сопряжение), [G463](../../../brain_matrica/cross-project-ideas/gotchas/G463.md)
> (утечка fff в `/tmp`).

## Что делаем

Ставим **OpenCode v2 (CLI + встроенный веб-UI)** на прод-бокс GONBA, но:

- сервер слушает **только loopback** (`127.0.0.1:49374`) — нового публичного порта нет;
- пул **анонимный**: без `auth login`, без ключей; работают бесплатные модели (лимит по IP);
  ⚠️ **Класс внешнего риска (предупреждение Мозга 18.10, #374):** с 17.10 все `opencode/*-free`
  могут начать отвечать `403 FreeTierError` («free tier can only be used from within OpenCode»)
  **с серверных IP** — при любом payload и пермишенах; аккаунт-ключ тир не поднимает, лечится
  платным ключом или выходом с другого egress. Наш бокс — того же серверного класса, поэтому
  если однажды **все** free-модели разом ответят 403 при живом маршруте и рабочем туннеле —
  это внешняя причина, а не поломка запускателя: проверяется одной попыткой с residential-выхода.
- вход в браузере — по одноразовой ссылке сопряжения (5 минут) → cookie-сессия ≈30 дней;
- наружу попадаем **через SSH-туннель** с компьютера владельца.

## Как входить (с компьютера владельца)

```bash
# 1. Туннель (алиас GONBA уже в ~/.ssh/config)
ssh -N -L 14974:127.0.0.1:49374 GONBA

# 2. Одноразовая ссылка (пароль не печатается — берётся на боксе из anon.env)
ssh GONBA "opencode-pair-link 49374 14974"
→ http://127.0.0.1:14974/auth/connect/<код>

# 3. Открыть ссылку в браузере своего компьютера
```

Одним кликом на Windows: `powershell -ExecutionPolicy Bypass -File scripts\opencode-web.ps1`
(поднимает туннель, берёт ссылку, открывает браузер).

**Ярлыки владельца (18.10, вечерняя пересборка).** На рабочем столе `D:\Desktop`:

- **`OpenCode Гоньба`** → `opencode-web.cmd -NoWait` (окно свёрнуто, `WindowStyle=7`, закрывается
  само; туннель остаётся поднятым). Если служба на боксе выключена — запуск поднимает её сам
  (`sudo -n systemctl start` + ожидание ответа `/api/info` на боксе, до 45 с) и печатает ссылку входа.
- **`OpenCode Гоньба (выключить)`** → `opencode-web-off.cmd` (флаг `-Off`): гасит **службу на боксе**
  (замер: 178 МБ в простое, 347–450 МБ разогретой; RAM бокса 1967 МБ) **и** закрывает туннель этого
  компьютера. Окно само закрывается через 8 с — чтобы успеть прочитать цифры, без нажатий
  (при ошибке держится 30 с и код выхода лаунчера не теряется: `exit /b %rc%`).
  Прежний ярлык `(отключить)` с `-Stop` (только туннель) удалён: владелец просил, чтобы при
  выключении бокс переставал тратить ресурсы вообще.

Туннель стартует **скрыто** (см. ниже) — окна `ssh.exe` на экране больше нет.
Копии на рабочем столе (`opencode-web.ps1`, `opencode-web.cmd`, `opencode-web-off.cmd`)
обновляются копированием из `scripts/`: после правок сверяй хеш, иначе ярлыки живут старым кодом.

**Переносимый запускатель (любой компьютер).** Файлы: `scripts/opencode-web.ps1` + `scripts/opencode-web.cmd` (Windows, двойной клик) и `scripts/opencode-web.sh` (Linux/macOS/Git Bash). На новом компьютере: запустил → если алиас `GONBA` есть, всё само; иначе `-Setup`/`--setup` заведёт цель, порты и ключ, сохранив `opencode-web.conf` рядом (локальный, в git не идёт). Проверка готовности: `-Check`/`--check`. Скрипт не содержит адреса бокса/пользователя — только алиас `GONBA` и порты, уже опубликованные в юните (функциональная необходимость).

**Каталог серверов и пульт (18.10, вечер — форма Мозга принята).** Мозг завёл каталог серверов (`docs/machines/servers/` в `brain_matrica`): один сервер — один фрагмент `<алиас>.conf` **в нашем диалекте**, раскладывает их на машины владельца он же. Предложенную форму — ключ `-Server <алиас>` плюс папка `servers\` рядом со скриптом — приняли как есть, с одним отличием: **нет фрагмента, значит остановка с перечнем того, что есть**, а не молчаливый откат к умолчаниям. Формулировка «файла нет — сегодняшнее поведение и умолчания» на практике означала бы, что опечатка в имени сервера молча ведёт владельца на **другой бокс**; в остальном форма Мозга не тронута. Сделано в обоих запускателях: `-Server`/`-Servers` (PowerShell) и `--server`/`--servers` (bash); `-Setup` с `-Server` заводит фрагмент на месте, если сервер добавляется не Мозгом. Фрагменты в git не идут (адрес и имя ключа — D-038), в репозитории только `scripts/servers/README.md`.

Живая проверка того же вечера: `-Servers` на пустой папке → фрагмент-зонд → `-Check -Server <зонд>` зелёный (служба `active`, 76 МБ, `/api/info` → 401) → запуск с `-Server` поднял туннель на **своём** порту и отдал ссылку входа → `-Stop -Server` закрыл ровно этот туннель (чужой на 14974 не тронут) → зонд удалён. Регрессия: `scripts/opencode-web.test.ps1`, третья часть — пять офлайновых сценариев разбора настроек плюс красное воспроизведение исходной формы (там же видно, что без защиты сценарий «фрагмента нет» становится зелёным по виду и неправильным по сути).

Второй сервер проверен там же по фрагменту Мозга: `es-vps` (он же `ispania_linux` — одна машина, два имени) — `-Check` зелёный (служба `active`, 207 МБ, `/api/info` → 401), запуск выдал ссылку входа; на том боксе **ничего не менялось** (чужой проект, живёт своей жизнью). `-Off`/`-On` на нём сознательно **не проверялись**: выключать чужую службу без слова владельца нельзя, это отдельный шаг. Мозг к тому же положил владельцу на рабочий стол готовые ярлыки с `-Config` (`opencode-web-es-vps.cmd` + `.conf`, `opencode-web-es-vps-off.cmd`, `opencode-web-sarafan.*`) — они работают и без папки `servers\`. Две формы сосуществуют и не спорят: `-Server` берёт фрагмент из `servers\` рядом со скриптом, `-Config` — явно указанный файл; смешивать в одном запуске не нужно.

**Граница с пультом.** Сам «пульт» над серверами — артефакт Мозга (D-143: пульт + сторожа серверов; соты-ферма не возвращается). Наша половина — клиентский запускатель и раскладка на машине; второй установщик Мозг не пишет, формат `-Setup` развивается расширением, а не вторым скриптом.

Тонкость (грабля клиента): OpenSSH для Windows не завершает процесс и не отдаёт вывод, если его std-хендлы перенаправлены (запуск не из консоли) — процесс висит, а вывод приходит с задержкой ≈9 секунд. Запускатель ждёт в выводе маркер `OC_DONE:<код>` и добивает ssh, чтобы не оставлять зомби; в интерактивной консоли ssh завершается сам. В неинтерактивной среде каждый вызов бокса стоит ≈10 секунд — это ожидаемо.

### Находки 2–3 письма Мозга: класс повтора и сверка цели туннеля (19.10, сделано)

18.10 вечером Мозг прогнал ярлык живьём с COMPUTER до чужого бокса (канал шёл через ВПН владельца) и прислал три находки. Первая — тихий `-LocalPort` — была закрыта ещё каталогом (`Resolve-OcSettings`: параметры командной строки старше файла); две оставшиеся доделаны 19.10.

**Потолок согласования и повтор по классу.** Сессия к боксу ходила с `ConnectTimeout=8`, а повтор запроса ссылки срабатывал только на собственный 60-секундный таймаут запускателя. На деградировавшем канале banner exchange занимал 10–15 с, ssh выходил **сам** по своему потолку, и повтор этого не ловил: пять мёртвых окон подряд, при том что туннель (у него потолка нет) поднимался всегда, а в журнале бокса на каждый заход — `Connection closed by <адрес> [preauth]`. Теперь потолок — константа `$SshConnectTimeoutSec = 20`, а повтор заведён на **класс вывода** (`Test-OcRetryableSshFailure`): `timed out during banner exchange`, `Connection timed out`, `Connection closed by`, `Connection reset by peer`, `kex_exchange_identification` — то есть обрыв **до** аутентификации, где повтор и помогает. Отказ по ключу (`Permission denied`), неизвестный хост и пустой вывод в класс не входят: их повтор только затянул бы.

**Цель — часть опознания туннеля.** Прежде туннель искали по паре портов и не сверяли хост: форвард к **другому** серверу на том же локальном порту считался своим — ссылку входа запускатель брал у одного бокса, а UI открывался у другого. Уникальность портов `14974/14975/14976` — договорённость машин владельца, а не свойство. Теперь цель сверяется (`Test-OcTunnelCommandLine`: пара портов **и** цель последним аргументом; кавычки принимаем в трёх формах, потому что `Start-Process` склеивает строку сам), и это во всех путях — переиспользование, `-Stop`, `-Off`, пересоздание в `Repair-OcAccess`. Сравнение регистрозависимое, как у самого ssh: замер 19.10 — при `Host GONBA` в `~/.ssh/config` команда `ssh gonba` отвечает «Could not resolve hostname gonba».

**Заодно закрыт обратный случай — «порт слушает» ≠ «слушает наш ssh».** `New-OcTunnel` считал успехом любой занятый порт, поэтому чужой форвард (или посторонний процесс) выдавался за свой туннель. Теперь успех — порт, занятый **именно этим** процессом ssh (`Test-OcPortMine` через `Get-NetTCPConnection -LocalPort … -State Listen -OwningProcess`); если проверить владельца нечем (старая Windows без NetTCPIP), поведение прежнее. `-Stop`/`-Off` чужой туннель больше не гасят, а честно говорят, что порт держит не наш туннель.

**Проверено на живом (19.10, эта машина, прод не тронут):** свой туннель, поднятый настоящим `ssh`, `-Stop` узнал и снял (процесс завершился, порт свободен); посторонний слушатель на том же порту `-Stop` **не** тронул — сказал «держит не наш туннель», вернул 1, слушатель остался жив; приписывание порта процессу сошлось (свой pid → True, чужой → False). Офлайновая регрессия — четвёртая часть `scripts/opencode-web.test.ps1`: 20 сценариев (класс повтора на реальных текстах ошибок, командные строки форвардов) + красное воспроизведение исторической формы «по паре портов» + пять привязок в самом запускателе, чтобы рефакторинг не мог оставить правильную функцию, но вернуть старый вызов.

**Состояние цели изменилось — это надо помнить.** 19.10 движок (Пасека) снят с прод-серверов: `/usr/local/bin/opencode` на боксе нет, юнит `opencode-web` `inactive` и `disabled`. Значит живой путь (ssh → туннель → ссылка входа) на GONBA проверять больше не на чем, и первая часть регрессии честно печатает `живой путь: N/A (движка на боксе нет)`, а не «зелено»; проверяемым остаётся то, что `-Check` доходит до конца и возвращает 0. Порт `49374` и сторожа при этом живы (`opencode-web-watchdog.timer` — `active`), то есть запускатель остаётся рабочим инструментом на случай, если движок вернут.

**Расхождение, которое не спрятано:** bash-версия (`scripts/opencode-web.sh`) этих правок не получила — она вообще осталась на ревизии #314 и не знает ни `-Stop`/`-Off`, ни сверки живости туннеля; `ConnectTimeout=8` там тоже остался. Чинить её — отдельной задачей, а не попутно.

### Проверка запускателя: `-Check` доказывает не всё

17.10 `-Check` был зелёным, а двойной клик по ярлыку падал:

```
Невозможно вызвать метод для выражения со значением NULL.
...opencode-web.ps1:178   +     return @{ status = $status; code = $code; out = $text; err = $err ...
FullyQualifiedErrorId : InvokeMethodOnNull
```

Причина: при двойном клике из настоящей консоли ssh на Windows не пишет в stderr ничего, `Get-Content -Raw` на пустом файле отдаёт `$null` (а не пустую строку), и `.Trim()` по нему — исключение. Падало сразу после подъёма туннеля, до ссылки входа. Неинтерактивный прогон этот случай маскировал (там ssh добавляет в stderr предупреждение `GetConsoleMode`, файл не пуст) — то есть зелёный `-Check` **не доказывал** работоспособность ярлыка (pool #011, «зелёный пайплайн ≠ корректный результат»). Лечение: `Read-OcRawText` в запускателе + регрессия, которая подставляет **реально пустой** stderr в две копии — с нулевой защитой и без неё:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\opencode-web.test.ps1
→ RED: копия без защиты падает (InvokeMethodOnNull) · GREEN: текущая проходит -Check · E2E: двойной клик отдаёт ссылку
```

Копия без защиты собирается из текущего файла вырезанием строки-защиты, так что тест самодостаточен (не зависит от старых версий). Нужен ssh-доступ к боксу. E2E-шаг идёт только при уже поднятом туннеле — чтобы не оставлять за собой лишнее окно ssh; если ssh не отдал вывод за 60 с, тест помечает e2e как `inconclusive`, а не как успех.

### Туннель без окна и выключатель `-Stop` (18.10)

Владелец сформулировал боль прямо: «без всплывающих и мешающихся окон терминала». Замер подтвердил,
что жалоба точная: у процесса туннеля было **живое окно консоли** — `(Get-Process ssh).MainWindowHandle`
= **395146**, заголовок `C:\Windows\System32\OpenSSH\ssh.exe`, и оно висело ровно столько, сколько
живёт туннель (то есть всегда, пока работаешь). Правка: туннель стартует через
`Start-Process … -WindowStyle Hidden` → `MainWindowHandle=0`, форвардинг проверен (`/api/info` → `401`
через туннель). Окно запускателя при `-NoWait` закрывается само, а туннель остаётся поднятым —
закрывает его `-Stop`: ищет ssh по строке `-L <локальный>:127.0.0.1:<удалённый>` (окна у него нет,
командная строка — единственный след), идемпотентен (повтор отвечает «закрывать нечего» и выходит `0`),
а если порт остался занят — говорит об этом и выходит `1`. Проверено на живом прогоне:
`pid=1948 windowHandle=0` → `-Stop` → «порт 127.0.0.1:14974 свободен».

### Включение-выключение самой службы: `-Off` (18.10)

Владелец: «хочу, чтобы opencode не занимал ресурсы прод-сервера, когда я им не пользуюсь». Роли разделили:

- **запуск без ключей** — туннель + (если служба выключена) поднимает её + ссылка входа;
- **`-Stop`** — закрывает только туннель этого компьютера, служба на боксе продолжает есть память;
- **`-Off`** — гасит **службу на боксе и** туннель этого компьютера.

Замер живого цикла: `-Off` → `MemoryCurrent 347 МБ → [not set]`, доступная память бокса
`666 → 889 МБ`, порт 14974 свободен, exit 0; повторный `-Off` идемпотентен («служба уже
остановлена»). Обратный путь: обычный запуск при выключенной службе → «включаю» → `сервер отвечает
(код 401)` → туннель, суммарно 9,2 с. Клики через реальные обёртки рабочего стола прогнаны оба.

**Служба остаётся выключенной — это проверено, а не подразумевается.** Контроль после `-Off`:
три `-Check` подряд (0 с, 30 с) дают `failed`/`inactive`, автостартеров на боксе нет:
`opencode-tmp-sweep.timer` ходит по сетке :00/:15 и `systemctl start` не дёргает (единственный раз,
когда старт нашли в журнале, — 15:43:09, это явный клик запуска), в `/etc/cron.d` на opencode
ничего нет. То есть выключатель держит, пока сам владелец не запустит обратно.

Грабля, на которую ушло время (записана комментарием в коде): в шапке скрипта объявлен ключ
`[switch]$Stop`, а `$stop = Stop-OcService …` — **тот же самый слот**: PowerShell не различает регистр,
и присваивание хеш-таблицы в switch падает
`ArgumentTransformationMetadataException: Hashtable → SwitchParameter`, причём стек указывает на
строку вызова функции, а не на присваивание — ищи переменную-двойника, а не баг внутри функции.
Лечение — имя `$stopResult`.

`SuccessExitStatus=130` в юните: приложение по SIGTERM завершается кодом **130**, и systemd писал
штатную остановку как `failed`. После правки `systemctl stop` даёт `inactive`, `-Off` и `-Check`
показывают «остановлена», а настоящие падения (SIGKILL → 137) остаются сбоем и триггерят
`Restart=on-failure`. Юнит применён на бокс (`install` + `daemon-reload`, без рестарта работающей
службы) и лежит в `deploy/systemd/opencode-web.service` — деплой сам сверит `cmp` и доедет.

### Зависший сервер: «служба активна и молчит» (18.10.2026, вечер)

Владелец: «не могу подключиться, пишет что тоннель уже есть а сервер упал, пытается его
перезапустить, но не выходит, и так по кругу». Ярлык «выключить» (`-Off`) в этом состоянии
тоже «не срабатывал».

Что было на самом деле: юнит **активен**, сервер **молчит**. Замеры до вмешательства:
`MemoryCurrent 548 МБ` при `MemoryHigh=500M`, до жёсткого `MemoryMax=700M` не дошёл →
`memory.pressure some avg10=100.00 full avg10=99.00`,
`NRestarts=0` — ядро никого не убило, `Restart=on-failure` не сработал. На боксе при этом
было **351 МБ доступно** и `load average 5.02` на одном ядре, а `curl` на
`127.0.0.1:49374/api/info` давал таймаут (код 28). То есть сервер задохнулся **внутри своего
потолка** и перестал отвечать, оставаясь живым; `ssh` на бокс отвечал за секунды.

Почему ярлык зацикливался — два дефекта, оба в запускателе:

1. Живость службы он проверяет **HTTP через туннель**, а молчащая служба и выключенная дают
   один и тот же ноль. Отсюда честная, но ложная строка «служба выключена — поднимаю её» и
   `systemctl start` по **уже активному** юниту: пустая операция, из цикла выхода нет.
2. `-Off` проигрывал гонку: в юните `TimeoutStopSec` был дефолтный **90 с**, а сессия ждала
   ровно столько же — даже прошедшая остановка докладывалась как «бокс не ответил».

Что теперь:

- **тупик разбирается вопросом к боксу** — одна ssh-сессия, и только в тупике
  (`Repair-OcAccess`): не активна → `start`; активна и отвечает на боксе → виноват туннель,
  пересоздаём (`Restore-OcTunnel`); активна и молчит → `restart`. Здоровый путь по-прежнему
  не тратит ни одной ssh-сессии и ни одной секунды;
- **`-Off`** ждёт до 150 с и внутри той же сессии дожидается выхода юнита из `active`;
  в юните `TimeoutStopSec=30`, поэтому задохнувшийся сервер умирает за 30 с, а не за 90;
- **туннель считается живым только при живом SSH-соединении** (`Test-OcTunnelLive`), а не по
  «порт слушает»: 18.10 на порту 14974 висели сотни сокетов в `CLOSE_WAIT` — порт принимал
  соединения, а форвардить было некуда;
- **сторож** (новое): `scripts/opencode-web-watchdog.sh` → `/usr/local/bin/opencode-web-watchdog`
  + `opencode-web-watchdog.{service,timer}`. Раз в 2 минуты: юнит активен и `curl /api/info`
  отвечает `000` три проверки подряд → `restart` и запись в журнал. Выключенную владельцем
  службу (`-Off`) сторож не трогает — это решение владельца, а не авария. Скрипт и юниты
  ставит **деплой** (root-owned, из репо), а не руки: файл, который никто не исполняет, — не
  источник правды. Проверка сторожа вхолостую, без единого рестарта:
  `sudo OC_WD_DRY=1 OC_WD_LIMIT=1 OC_WD_PORT=9 /usr/local/bin/opencode-web-watchdog`.
  **Цена лечения, о которой надо знать:** `restart` обрывает активные сессии улья — но он
  случается только после ~6 минут молчания, то есть когда UI и так не отвечает.
- **регрессия** — вторая часть `scripts/opencode-web.test.ps1`: пять сценариев тупика на
  подставном боксе (заглушки вместо ssh) плюс воспроизведение исторической логики «любой тупик
  = поднимать». Полностью офлайновая, прод не трогает.

**Приёмка на живом боксе (после деплоя `39159450503`, 22:37–23:00).** Таймер
`opencode-web-watchdog.timer` — `enabled/active`, прогоны каждые ~2 минуты («Finished»);
скрипт в `/usr/local/bin` root-owned и `cmp`-идентичен репо; у юнита `TimeoutStopUSec=30s`;
сервер `active`, loopback `/api/info` 401, давление 0.00. Холостой прогон сторожа печатает
диагноз и **не** перезапускает; контроль «юнит не `active`» — молча выходит. Главное:
в окне, когда служба была выключена ярлыком (22:56:36–22:59:00), сторож отработал в 22:57:49
и **не** тронул её — свойство «выключенная служба не наша забота» проверено на реальном
юните, а не на заглушке. Полный цикл «выключить → включить»: `-Off` → «остановлена»,
память службы 159 МБ → `[not set]`, на боксе 787 → 842 МБ, туннель закрыт, exit 0;
запуск → «служба `inactive` — поднимаю её» → «сервер отвечает (код 401)», **11 с** на всё
(туннель + вопрос к боксу + старт + ссылка).

Честная граница: **точная причина именно этого зависания не доказана** — замер снят уже после
перезапуска, и тяжёлого ребёнка (как `npx tsc` в утреннем инциденте 18.10) в cgroup не было.
Подпись однозначная (стопор в зоне `MemoryHigh` без OOM), но сторож закрывает **класс**, а не
эту конкретную причину.

**Решение владельца по потолкам (18.10, его слово):** `MemoryHigh=500M` / `MemoryMax=700M`
**оставить как есть**. Причина — сторож закрывает класс и лечит не только память, а коридор
не поднимали потому, что вместе с ним уезжает вверх и зона стопора, тогда как на боксе ~790 МБ
доступно и рядом живут шесть чужих Next-серверов. **Триггер возврата:** сторож перезапускает
службу повторно, и в журнале это видно без тяжёлых детей внутри улья.

### Почему вход ждёт минуту: sshd бокса под сканерами (замер 18.10, значение подтверждено)

Прежнее «фон интернета» доведено до факта. `sudo -n sshd -T` на боксе: **`maxstartups 10:30:100`** —
это дефолт, и свой `/etc/ssh/sshd_config.d/10-hardening.conf` его не трогает (там только
`PasswordAuthentication no`, `PermitRootLogin prohibit-password`, `PubkeyAuthentication yes`);
`persourcemaxstartups none`; `OpenSSH_9.6p1 Ubuntu-3ubuntu13.20`. Одновременно в
`ss -tan state syn-recv` висело **81** полуоткрытое соединение от чужих сканеров. При `10:30:100` это
ровно тот режим, когда sshd случайно отбрасывает часть новых подключений: замер дал **холодный вход
42,5 с** (следующий — 14,9 с), а одна сессия поймала **таймаут 60 с** и спаслась только повтором.
Это не «медленный бокс»: `load average` в тот момент был 0,00.

Что сделано на клиенте (сам отброс это не лечит, но снимает ложные «не работает»): потолок ssh-сессии
**30 с → `$SshSessionTimeoutMs = 60000`** (все четыре сессии `-Check` и запрос ссылки), ожидание
локального порта туннеля **15 с → 60 с**, повтор запроса ссылки остался. Тексты ошибок больше не
врут про 30 с.

**Вердикт (18.10, вечер): эти отбросы — НЕ причина медленного входа владельца.** Тот же час и тот же бокс:
`curl` и `.NET TcpClient` ходят к 22/80/443 за **63–78 мс** (`time_connect`), клиент Git-ssh **10.5p1**
логинится за **1,2 с**, а системный `ssh.exe` из `C:\Windows\System32\OpenSSH` (OpenSSH **7.7p1**, 2018 г.)
стоит в `connect()` **11–30 с** — таймстемпы `ssh -vvv` кладут дыру целиком между «Connecting to» и
«Connection established». Копия того же бинаря под другим именем ведёт себя одинаково (не «правило по
имени процесса»), TOS-метки DSCP (0/8/16/24/72) все быстрые (не они), VPN не при чём: бокс видит прямой
российский адрес, а общий трафик выходит через адрес в США. Лечение — **внутри запускателя**:
`Get-OcSshExe` выбирает лучший доступный клиент (сейчас `C:\Program Files\Git\usr\bin\ssh.exe`,
OpenSSH_10.5p1), а `-Check` предупреждает, если лучший старше major 9. Замер: `-Check` **92 с → 10,3 с**,
клик «запустить» **6,8 с**. Чтобы ручной `ssh GONBA` из консоли тоже был быстрым, инбоксовый клиент
обновляется одной строкой от имени администратора:
`Add-WindowsCapability -Online -Name OpenSSH.Client~~~~0.0.1.0`.

Серверный тюнинг — это **запас от бросов, а не лечение найденной поломки** (прямых отбросов мы ни разу
не поймали, а 81 в SYN-RECV при дефолтных `10:30:100` остаётся фактом):

- **Применено** `deploy/ssh/20-gonba-load.conf` → `/etc/ssh/sshd_config.d/20-gonba-load.conf`:
  `MaxStartups 50:30:150` и `LoginGraceTime 45`. Прогнано `sshd -t` → `systemctl reload ssh`;
  `sshd -T` отдаёт `maxstartups 50:30:150`, `logingracetime 45`, пароли по-прежнему `no`.
  Откат: `sudo rm /etc/ssh/sshd_config.d/20-gonba-load.conf && sudo systemctl reload ssh`.
  `50:30:150` вместо предлагавшихся `100:30:200`: сессия до авторизации ≈3 МБ, 150 таких ≈450 МБ
  из 1973 МБ при полном заполнении, а `200` ≈600 МБ уже теснит gonba/Postgres/nginx на 1 ядре.
- **Сознательно НЕ применено**: `PerSourceMaxStartups` (вход и деплой идут с общих адресов — CGNAT
  провайдера и раннеры GitHub; сосед-сканер на том же адресе выберёт лимит и отобьёт живой вход —
  риск залочиться больше выгоды); правка fail2ban (бани `bantime=600`/`maxretry=5` уже дают 426
  банов за 8 суток; удлинение бьёт по владельцу с динамического IP сильнее, чем по сканерам,
  а выгоды не замерено — см. `deploy/ssh/20-gonba-load.conf`, там тот же расклад в комментариях);
  `sysctl tcp_max_syn_backlog 128→1024` (синкокуки включены, рукопожатия 63–78 мс — лечить нечего).

Идея на будущее (не сделана): `-Check` ходит четырьмя ssh-сессиями — под таким sshd это 4× задержка
и 4 лишних слота; можно собрать в одну сессию с разбором одного вывода.

**Правка к прежней записи (18.10):** утверждение «`ss` без `-a` врёт» **не подтвердилось**. Перепроверено подряд на том же боксе: `ss -tn state syn-recv | wc -l` → **78**, `ss -tan state syn-recv | wc -l` → **78** (brain проверил у себя и получил то же). Дословную строку замера 17.10 («0 против 40») восстановить нельзя — она не сохранена, поэтому это **наша неточная запись**, а не грабля `ss`. Рабочая форма, которой мерили 18.10: `ss -tan | grep -c SYN-RECV`.


Почему не «просто порт наружу»: у сервера нет TLS, а внутри — агент с shell-доступом
к общему боксу, где живут чужие проекты и `/etc/gonba/gonba.env`. Туннель даёт тот же
браузерный UI без новой публичной поверхности.

Порт `49374` — дефолт OpenCode для Linux (одна константа в юните и документации).
Локальный порт `14974` выбран, чтобы не столкнуться с локальными пулами `:4096`/`:4097`.

## Ротация пароля сервера (17.10, проверено)

Источник истины по паролю — **файл окружения**, а не внутренняя база OpenCode: юнит грузит
`EnvironmentFile=~/.config/opencode-web/anon.env`, и сервер берёт `OPENCODE_PASSWORD` оттуда.
(Прежняя запись вида `opencode service set password <новый>` на нашей схеме лишняя — значение всё
равно перетирается файлом.)

```bash
# на боксе: новое значение + рестарт. Без sudo рестарт не пустит:
#   «Failed to restart opencode-web.service: Interactive authentication required.»
NEW="$(openssl rand -base64 48 | tr -d '/+=\n' | cut -c1-40)"
umask 077; printf 'OPENCODE_PASSWORD=%s\n' "$NEW" > ~/.config/opencode-web/anon.env
chmod 600 ~/.config/opencode-web/anon.env; unset NEW
sudo -n systemctl restart opencode-web
```

Проверка — три замка (все 17.10 сошлись): `/api/info` **без** пароля → `401`; `opencode api
--server http://127.0.0.1:49374 GET /api/info` **со** свежим `anon.env` → OK; `POST /api/pair`
без пароля → отказ, а `opencode-pair-link` с новым паролем → ссылку отдаёт (это и доказывает, что
ротация доехала до сервера, а не осталась в файле). Сам пароль в вывод не печатаем — только длину
и права файла.

Побочный эффект: рестарт рвёт cookie-сессию (≈30 дней) — владельцу достаточно одного двойного
клика по ярлыку, запускатель сам возьмёт свежую ссылку. Сайт рестарт агента не задевает: юниты
независимы, `gonba.service` не перезапускается.

## «Добрый сосед» (бокс общий: 1 ядро, ~650 МБ свободной ОЗУ, 6.9 ГБ диска)

- `Nice=5`, `CPUWeight=50`, `IOWeight=50` — под нагрузкой соседи важнее агента.
- `MemoryHigh=500M`, `MemoryMax=700M`, `MemorySwapMax=0`, `OOMScoreAdjust=200` —
  при нехватке памяти ядро убивает агента, а не Postgres/nginx/gonba.
  Замеры 17.10 шли вверх, и это важнее самих чисел: первый старт 362 МБ (пик 387 МБ, прогрев),
  через 5,5 ч — 252 МБ (пик 391 МБ), **а к вечеру, через 8,3 ч жизни, — 510 МБ при пике 525 МБ**,
  то есть вплотную к `MemoryHigh` (500 МиБ = 524 288 000 байт) при `MemoryMax` 700 МиБ.
  Вывод честный: «устоявшиеся 220–250 МБ» — это состояние первых часов, а не потолок.
  **Вечерний замер того же дня (22:48, аптайм 3,5 ч) закрыл открытый вопрос:** `systemd-cgls`
  показывает **один** процесс (`opencode serve`) и **ни одного** дочернего процесса модели —
  модель ходит по сети, локальных детей у сервера нет, то есть число держит сам сервер вместе
  с состоянием активной сессии. Числа: **426 МБ** при пике **500,4 МБ** (0,99 от `MemoryHigh` —
  порог задет, но не пробит; `NRestarts=0`, oom 0). Рост немонотонный (510 → 426 МБ), значит
  цифра идёт за нагрузкой, а не течёт сама. Оговорка: сессия, которая мерила, живёт в том же
  cgroup и её состояние — часть числа.
  **Суточный замер 18.10 ответил на открытый вопрос — ответил инцидентом.** К утру аптайм был
  15,3 ч, `MemoryCurrent` **617 МБ** (сервер 377 МБ + **215 МБ зависшего `npx tsc --noEmit`**),
  cgroup — **100 % memory pressure**, `ss` показывал **89 неподнятых соединений**, `/api/info` не
  отвечал вовсе: веб-UI владельца перестал открываться, и он полдня считал, что сломался ярлык.
  Причина — **дочерний процесс самого агента**: сессия улья запустила проверку типов в 02:51, та
  встала в `D`-состояние на 7,5 ч и съела память внутри того же потолка. То есть число растёт не
  «само» и не от модели: его растит работа, которую агент делает **внутри своего же cgroup**.
  Лечение (прод-операция, разрешена владельцем в том же ходе): `sudo systemctl restart opencode-web`
  → **144 МБ**, очередь 0, `/api/info` → `401`; на боксе доступно стало **840 МБ против 282 МБ**,
  `load average` 6–8 → 0. Решение по потолку остаётся за владельцем: поднимать `MemoryHigh` теперь
  есть куда, но 18.10 показал, что цифру растит в первую очередь лишняя работа, а не потолок.
  Потолок 700 МБ выбран сознательно: пусть ядро убьёт агента, а не уведёт в swap общий бокс;
  поднимать — только по замеру, помня про ~670 МБ доступной ОЗУ и 808 МБ занятого swap.
- `StartLimitBurst=5/300s` — цикл падений не превращается в молотилку.
- **Никаких сборок на боксе.** Канон проекта: сборка — в CI (`deploy-prod.yml`),
  на боксе только рантайм. Прогон `npm run build` на этом боксе бьёт соседей.
- **И проверок типов/линта тоже — 18.10 это стоило суток недоступного веб-UI.** `npx tsc --noEmit`,
  запущенный агентом внутри юнита, съел 215 МБ в общем с сервером cgroup и задушил сервис (разбор —
  в разделе про память). Для агента это не «тяжеловато», а **задушить себя**: память и потолок у
  него общие с его же дочерними командами. Практическое следствие для сессий улья: локальные гейты
  (`typecheck`/`lint` перед мержем) в улье заменены зелёным CI — гейт остаётся, но гоняет его чужая
  машина (#125: гейты гоняет CI, не рука). Жёсткий `deny` — см. «Политики».
- `PrivateTmp=yes` — утечка fff (G463) не попадает в общий `/tmp` бокса.

### Чего агент в улье не может — и почему это свойство установки, а не случайность

`sudo *` и чтение `/etc/gonba/*` запрещены политикой, плюс в юните стоит `NoNewPrivileges=yes`.
Следствие, которое надо помнить при планировании работ: **изнутри улья невозможны замеры по
прод-БД, правки юнитов, рестарты сервисов и любые прод-операции** — это делает сессия с `sudo`
(Claude Code на боксе). Замер, который агент улья всё-таки может: `systemctl show`/`systemd-cgls` по
своему юниту, `journalctl` по нему, `/api/health` сайта, `git grep` по репозиторию.
Обратная сторона — полезная: агент улья не может случайно сломать прод, а гейт #025 для него
не «спросить и забыть», а физическая невозможность.

## Политики (жёсткие запреты)

`deploy/opencode/opencode.json` переносит канон `.claude/settings.json` на бокс и добавляет
бокс-специфику: `deny` на `git push origin main|master` (все формы, включая force),
`gh workflow run deploy*`, `sudo *` и чтение `/etc/gonba/*` (прод-секреты).
Политики — не «спросить», а жёсткий блок: их нельзя снять одобрением в UI.

18.10 сюда добавились тяжёлые команды, которыми агент задушил сам себя: `npx tsc *`,
`npm run build*`, `npm run typecheck*`, `npm run lint*`, `npm --prefix * run build*`. Это не «запрет
проверок» — проверки остаются, но их гоняет CI; внутри улья они бьют по тому же cgroup, что и
сервер. **Честная граница:** это блок против случайности, а не граница безопасности (`bash -lc "…"`
его обойдёт), и он не заменяет канон: сессия улья и её человек должны знать, что в улье гейт — CI.

Важно: репозиторный файл — только происхождение, политику применяет **копия на боксе**
(`~/.config/opencode/opencode.json`). Правя одну, скопируй на бокс и сверь `diff`.

Плюс `NoNewPrivileges=yes` в юните: `sudo`/`su` внутри юнита не работают даже без политики.
Прод-операции (рестарты, миграции) остаются за владельцем — по канону #025.

## G463 — утечка `/tmp` (почему это отдельная забота)

Наш бокс — Linux, а платформенная граница по этой грабле в экосистеме не разведана:
у Мозга и корпуса второго opencode на Linux-боксе нет, а у SARAFAN 15.10 утечка съела
диск до 100% и уронила Postgres. Поэтому:

1. `PrivateTmp=yes` — сервис пишет в свой `/tmp` (чистится при остановке юнита);
2. `opencode-tmp-sweep.timer` каждые 15 минут сносит в `/tmp` и `/var/tmp` файлы вида
   `*-00000000.so` / `*-00000000.dylib` старше 60 минут — страховка для запусков вне юнита;
3. замер до/после первого запуска (см. «Приёмка») — вклад в разведку платформы.

## Глаза: headless-браузер на боксе (директива brain 17.10 — выполнена)

Зачем: бокс безголовый, модель не видит ни создаваемого интерфейса, ни GUI вообще. Ставим локальный
Chromium **без окон**: агент сам открывает свой сайт, снимает PNG и читает его как картинку.

```bash
# 1. браузер — user-local, без sudo, ноль системных изменений (проверено 17.10)
npx -y playwright@latest install chromium          # 681 МБ в ~/.cache/ms-playwright

# 2. снимок интерфейса: PORT — порт dev-сервера, который строит сессия (локальный 127.0.0.1)
npx playwright screenshot --viewport-size=1440,900 --wait-for-timeout=5000 \
  http://127.0.0.1:PORT shot.png
# → дальше модель читает shot.png как изображение
```

Модель нужна **с vision** — по названию в нашем пуле такая одна, `nemotron-3.5-super-vl-free`
(«vl»; картинкой ещё не проверяли — проверить при первом живом использовании); текстовые free
(`deepseek-v4.1-flash-free`, `big-pickle` и прочие) картинок не читают, для «посмотри» модель
переключают в сессии. **Скрины остаются на боксе** (на экране бывает что угодно) — в письма
и репозиторий их не таскать.

**Три факта, добытых замером (портативны, отписаны Мозгу):**

1. **`npx playwright screenshot` работает как есть, а сырой бинарь полного Chrome — нет.**
   На Ubuntu 24.04 стоит `kernel.apparmor_restrict_unprivileged_userns=1`: песочница пространств
   имён запрещена политикой, поэтому `chrome --headless=new` в юните с `NoNewPrivileges=yes`
   завершается `rc=134` (abort, core dump). С `--no-sandbox` тот же бинарь страницу снимает.
   Канонической команде флаг не нужен — Playwright идёт через `chrome-headless-shell`.
2. **`sudo apt-get install chromium` на Ubuntu 24.04 — тупик:** у пакета `chromium` кандидата нет
   вовсе, а `chromium-browser` — snap-заглушка (`2:1snap1-0ubuntu2`). Рабочий путь один — Playwright.
3. **Система бокса не менялась:** отсутствующие mesa-пакеты (`libegl-mesa0`, `libgl1-mesa-dri`,
   `libglx-mesa0`, `mesa-libgallium`, `mesa-vulkan-drivers`) скриншотам не мешают, `--with-deps`
   не понадобился. Цена — 681 МБ `~/.cache/ms-playwright` + ~270 МБ npm-кэш (диск бокса 78% → 80%).

```bash
# 0. предпосылки: gcc-подобные — не нужны, бинарник статичный ELF x86-64 (glibc 2.39, avx2 есть)

# 1. бинарник (архив, без curl|bash)
curl -fsSL -o /tmp/opencode-linux-x64.tar.gz \
  https://opencode.ai/update/api/latest/cli/opencode/opencode-linux-x64.tar.gz
tar -xzf /tmp/opencode-linux-x64.tar.gz -C /tmp/oc-install
sudo install -m 0755 /tmp/oc-install/opencode /usr/local/bin/opencode
opencode --version

# 2. каталоги и пароль (пароль не печатать в чат/логи)
mkdir -p ~/.config/opencode-web ~/.local/share/opencode-anon ~/repo
chmod 700 ~/.config/opencode-web
[ -s ~/.config/opencode-web/anon.env ] || \
  printf 'OPENCODE_PASSWORD=%s\n' "$(openssl rand -base64 48 | tr -d '/+=\n' | cut -c1-40)" \
  > ~/.config/opencode-web/anon.env
chmod 600 ~/.config/opencode-web/anon.env

# 3. глобальный конфиг с политиками
mkdir -p ~/.config/opencode
cp ~/GONBA/deploy/opencode/opencode.json ~/.config/opencode/opencode.json

# 4. рабочий клон (не боевой!)
# Реальный путь после переезда 17.10 — ~/repo/Gonba; на этой машине путь в юните
# (~/work/GONBA) жив ярлыком. На НОВОЙ машине ярлыка не будет: либо клонируй
# в ~/work/GONBA, либо поправь WorkingDirectory юнита на реальный путь.
[ -d ~/repo/Gonba ] || git clone https://github.com/Valstan/Gonba.git ~/repo/Gonba

# 5. юниты и метёлка
# ВНИМАНИЕ (18.10.2026): этот ручной блок — только для НОВОЙ машины. На боевом боксе юниты
# и скрипт сторожа обновляет деплой (`.github/workflows/deploy-prod.yml`: cmp + cp из репо,
# для таймеров reenable + restart), поэтому руками их больше править не нужно — иначе репо
# и бокс разъедутся молча. Ручными остаются только метёлка и pair-link.
sudo cp ~/GONBA/scripts/opencode-tmp-sweep.sh /usr/local/bin/opencode-tmp-sweep
sudo chmod 0755 /usr/local/bin/opencode-tmp-sweep
sudo cp ~/GONBA/scripts/opencode-pair-link.sh /usr/local/bin/opencode-pair-link
sudo chmod 0755 /usr/local/bin/opencode-pair-link
sudo cp ~/GONBA/deploy/systemd/opencode-web.service \
        ~/GONBA/deploy/systemd/opencode-tmp-sweep.service \
        ~/GONBA/deploy/systemd/opencode-tmp-sweep.timer \
        ~/GONBA/deploy/systemd/opencode-web-watchdog.service \
        ~/GONBA/deploy/systemd/opencode-web-watchdog.timer /etc/systemd/system/
sudo install -m 0755 ~/GONBA/scripts/opencode-web-watchdog.sh /usr/local/bin/opencode-web-watchdog
sudo systemctl daemon-reload
sudo systemctl enable --now opencode-web.service
sudo systemctl enable --now opencode-tmp-sweep.timer
sudo systemctl enable --now opencode-web-watchdog.timer
```
