## Следующий шаг

**Снять приёмку классификатора заново — на новом лимите токенов.** Приёмка 09.09 показала, что проверять правила было нечем: модель молчала на 47 % вызовов, и молчала **ровно на тех записях, которые правила должны разводить**. Причина найдена и починена (раздумья съедали весь `max_tokens`), фикс на проде. Нужно дождаться нескольких прогонов и посмотреть вердикты:

```bash
scp q.sql GONBA:/tmp/q.sql
ssh GONBA 'set -a; . /etc/gonba/gonba.env; set +a; psql "$DATABASE_URL" -f /tmp/q.sql'
```

(SQL — файлом, не через `psql -c`: D-046.)

Смотреть три вещи:

1. **Доля `fallback` упала?** Была 47 % (8 из 17 с 25.08). Обрезание по бюджету теперь имеет **отдельную** причину в `rationale` — если оно вернётся, будет видно сразу и не спутается с молчанием.
2. **Вердикты по существу:** записи из общей группы села (`218688001`) должны перестать оседать на `gonba`.
3. **Доля попаданий в префиксный кэш** — теперь пишется в `vk_classification.usage`, считается обычным SQL.

Дальше по порядку, не перепрыгивать: приёмка → расхождения править **текстом правил в админке**, не кодом → и только потом запрет, с одного источника и первым шагом без запрета.

- **Классификатор: 47 % вердиктов терялись молча — причина найдена и починена.**
  - **Замер:** с доставки ключа 25.08 — 17 классификаций, 8 в `fallback` с «пустым результатом».
  - **Гипотеза «длина поста» опровергнута:** ответившие в среднем 4114 символов, молчавшие 3093 — диапазоны перекрываются.
  - **Корреляция с источником:** общая группа села дала 6 пустых из 7, все прочие источники — 2 из 10. Модель молчала ровно там, где нужны правила, и отвечала на «опубликовано от имени проекта X».
  - **Причина — живым опытом, тот же промпт, разный лимит:** `max_tokens: 2000` → `finish_reason: length`, content пустой, `reasoning_tokens: 2000` из 2000; `max_tokens: 8000` → `stop`, `reasoning_tokens: 637`, ответ на месте. **Токены раздумий входят в `max_tokens`** — это был открытый вопрос в комментарии к самой константе.
  - **Починено:** лимит 8000; обрезание по бюджету получило отдельную причину в `rationale` (раньше `finish_reason` выбрасывался, и лечение было неотличимо от бесполезного); `usage` с hit/miss кэша пишется в `vk_classification`.
- **Две мины в `deploy-prod.yml`, найденные чек-листом brain и починенные:**
  - **G322:** `ssh … "npm install … | tail -5"` — конвейер на удалённой стороне, код выхода отдаёт `tail`, упавший install уезжал зелёным. Ломались бы таймеры `vk-sync`/`media-cache`, то есть не сайт → нашлось бы поздно.
  - **G321:** `ssh 'bash -s' "$SHA"` при пустом аргументе давал `REL="$BASE/releases/"`, и следующая строка `rm -rf` снесла бы **весь каталог релизов вместе с откатом**. Добавлен гвард.
  - Обе проверены **контроль-негативом**, не глазами: без `pipefail` — код 0 на упавшей команде, с ним — 7; гвард на пустом SHA — выход 1 до деструктивной строки.
- **Расписание VK-синхронизации задано владельцем явно: 06/10/13/18/23 MSK.** Гард интервала оставлен только как защита ручного триггера и получил допуск 5 минут.
