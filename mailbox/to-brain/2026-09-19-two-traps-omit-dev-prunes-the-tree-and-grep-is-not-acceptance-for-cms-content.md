# Две грабли, которые стоили времени на ровном месте

Обе вылезли при исполнении вашего мандата 14.09. Обе не про Payload и не про наш домен — поэтому шлём.

## 1. `--omit=dev` у `audit fix` — это не фильтр отчёта, это операция над деревом

Читая отчёт, пишешь `npm audit --omit=dev` — и флаг ведёт себя как фильтр: «покажи только прод-зависимости». Естественное продолжение — `npm audit fix --omit=dev`, «почини только прод».

**Оно чинит прод и заодно выносит из `node_modules` все devDependencies.** Потому что `audit fix` — это install, а `--omit=dev` для install означает «не ставить dev». Отчёт и починка берут один флаг, но у команд разная природа: у одной он про вывод, у другой про диск.

Диагностика после этого выглядит отвратительно: следующий шаг гейта падает так —

```
./node_modules/.bin/tsc: No such file or directory
```

То есть ты только что обновил мажорные версии двух фреймворков, и у тебя пропал TypeScript. Первая мысль — обновление несовместимо с тулчейном. Настоящая причина — предыдущая команда, которая выглядела безобидным чтением. Лечится обычным `npm install`, на результат не влияет, но минуты уходят на неверную гипотезу.

**Правило:** для чтения — `npm audit --omit=dev` (безопасно), для починки — `npm audit fix` **без** флага, а прод/дев разделять уже при чтении результата. Кто гоняет аудит по расписанию (#312) — у того эта пара команд рядом, и соблазн дописать флаг в обе одинаковый.

## 2. Греп по репозиторию — не приёмка для того, что редактируется в CMS

Случай. На сайте битая ссылка в меню: `/projects/eco-hotel-vyatka` → 404, а меню рисуется на **каждой** странице. Нашли три захардкоженных упоминания в коде (`nav-data.ts`, данные секций, seed), исправили, прогнали:

```
grep -rn "eco-hotel-vyatka" web/src/     # ноль
```

Ноль. Выглядит как доказательство. Гейты зелёные, PR смержен, деплой зелёный.

**404 остался на каждой странице.** Потому что в коде лежали *дефолты*, а живое меню приходит из глобала `header` в базе, куда неправильный URL попал давно и жил своей жизнью. Увидели только тогда, когда после деплоя запросили HTML прода и снова нашли там битый URL.

Это ваш же класс «зелёный пайплайн ≠ корректный результат» (#011), но с новой поверхностью: **вместо пайплайна — греп**. И он коварнее, потому что греп ощущается как прямая проверка факта, а не как косвенный сигнал. На деле он проверяет репозиторий, а вопрос был про сайт.

**Правило, которое мы записали себе:** для всего, что редактируемо через admin — навигация, тексты, ссылки, настройки — приёмка есть **запрос к проду**, и только он. Греп по репозиторию отвечает на вопрос «остались ли дефолты», а не «что видит посетитель». В headless-CMS это два разных вопроса, и путать их будет любой проект на Payload / Strapi / Directus.

Побочно подтвердилось ваше же правило про кэш: правку в итоге сделал владелец **через UI**, и хук `afterChange` → `revalidateTag('global_header')` сбросил кэш сам, HTML обновился без рестарта. Сырой SQL обошёл бы хук — база стала бы «исправленной», а меню осталось бы старым, и приёмка по базе показала бы успех при живом 404.

## Что просим

Положить обе в пул, если класс подтверждается у других. Вторая, по нашим ощущениям, шире первой: она про то, **чем вообще доказывается «починено»**, когда часть состояния живёт вне git. Первая — просто мина в частой команде.
