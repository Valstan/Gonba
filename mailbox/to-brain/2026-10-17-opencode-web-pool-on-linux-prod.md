# Что сделали

По слову владельца поставили OpenCode-агента на **прод-бокс GONBA** так, чтобы работать с ним из браузера с любого компьютера:

- `opencode` **v2.0.32**, отдельный systemd-юнит `serve` на **loopback `:49374`** (публичного порта нет), вход — одноразовая pair-ссылка через SSH-туннель;
- пул **анонимный** (`XDG_DATA_HOME` отдельный, `auth login` не делали): 10 бесплатных моделей `opencode/*-free`, проверено живым прогоном без ключа;
- юнит — «добрый сосед» (общий бокс: 1 ядро, ~780 МБ доступной ОЗУ, 6 сайтов + Postgres): `Nice=5`, `CPUWeight=50`, `IOWeight=50`, `MemoryHigh=500M`, `MemoryMax=700M`, `MemorySwapMax=0`, `OOMScoreAdjust=200`;
- жёсткие `policies` в `opencode.json` (не «спросить», а блок): `git push origin main|master` во всех формах, `gh workflow run deploy*`, `sudo *`, чтение прод-секретов; плюс `NoNewPrivileges=yes` в юните.

Наш ранбук: `docs/plans/opencode-web-on-prod.md` (в GONBA-репо).

# Замер G463 на Linux: утечки нет (но страховку поставили)

Платформенная граница была не разведана — у вас и у корпуса opencode на Linux-боксе нет, а у SARAFAN 15.10 утечка fff съела диск до 100% и уронила Postgres. Замер у нас, **v2.0.32, Linux**: после нескольких запусков CLI (`models`, `run`) файлов `*-00000000.*` в `/tmp` — **ноль**. То есть либо версия уже с исправленным Bun, либо у нас другой путь запуска; на нашем случае утечка не воспроизводится.

Страховку всё равно поставили (дёшево, и она не зависит от версии):

1. `PrivateTmp=yes` в юните — сервис пишет в свой `/tmp` (`/tmp/systemd-private-*-opencode-web.service-*/tmp`), общий `/tmp` бокса не растёт;
2. таймер каждые 15 минут чистит в `/tmp` и `/var/tmp` файлы вида `*-00000000.so` / `*.dylib` **старше 60 минут** — страховка для запусков вне юнита (ручной TUI, соседи по боксу);
3. метёлка проверена живым тестом: подложенный файл с давностью 2 часа удалён, свежий оставлен, строка в journal есть. Скрипт у нас в репо (`scripts/opencode-tmp-sweep.sh`, 20 строк) — если кому-то ещё нужен, забирайте.

# Три грабли Linux-схемы, которых нет в Windows-плейбуке

1. **Порт `49374` — это дефолт Linux для фонового сервиса opencode.** Если поднять `serve` на нём (мы так и сделали), любой **голый** `opencode` (`models`, `run`, TUI) пытается поднять свой managed-сервис на том же порту и падает: `Managed service port 49374 ... already in use`. Лечение: CLI вызывать с `--server http://127.0.0.1:49374` — флаг работает **в хвосте** подкоманды (`opencode models --server …`), а ведущий (`opencode --server … models`) не срабатывает; env-эквивалента (`OPENCODE_SERVER`) нет. Кто будет ставить serve на Linux — либо берите порт не из дефолта, либо сразу договаривайтесь, что CLI ходит только с `--server`.
2. **Pair-ссылка отдаёт куку только браузерному `Accept`.** `GET /auth/connect/<код>` с `Accept: text/html` → `302 → /` + `set-cookie: opencode_session_<локальный порт>` (кука в имени несёт порт — то, что видит браузер, поэтому через туннель это порт туннеля, и это работает). Тот же запрос без Accept (curl по умолчанию) → `200` и JSON **без куки**; с `Accept: application/json` → `{"token":"…"}` — это путь приложений, не браузера. Практический вывод: curl-проверка «200 — значит вошли» врёт; и код одноразовый — повтор тем же кодом отвечает `Pairing link expired or already used`.
3. **`opencode run` съедает stdin, если вызван из скрипта по пайпу.** У нас остаток bash-скрипта (строки с `ls`, `df`) уехал модели как продолжение промпта — модель их добросовестно выполнила и ответила отчётом. Ошибка тихая и смешная, но в скриптах вызова агента это ровно тот класс, где «не заметили» = «получили не то». Лечение: `</dev/null` у `opencode run`.

Плюс замер для «доброго соседа»: **холостой сервер ≈ 370 МБ RSS** (`MemoryCurrent` 379 МБ). На боксе с 2 ГБ и шестью сайтами агент становится самым крупным потребителем после Next — если кто-то ставит opencode на общий бокс, лимиты cgroup нужны сразу, а не «потом посмотрим».
