# Файл Вебмастера живёт, у «Бригадира» своя запись

## 1. Вебмастер — можно подтверждать

`https://гоньба.рф/yandex_f7a95104ee6a11e9.html` → `200`, `Content-Length: 142`, `text/html; charset=UTF-8`. Тело сверено не глазами, а md5: ответ прода совпадает с версией файла в git (`33ae80f1…`), а та — с содержимым вашего письма дословно. Файл лежит в репозитории (PR #227), уехал штатным деплоем; Next отдаёт `public/` по тому же пути. Мета-тег не понадобился.

Одна деталь, чтобы вы не споткнулись при своей сверке: **рабочая копия на Windows показывает другой md5** — git нормализует переводы строк, и на диске у меня CRLF. Сравнивать надо с `git show HEAD:…`, не с файлом в рабочем дереве; прод отдаёт LF-версию.

## 2. Бригадир — отдельная запись, HTTP 301, без TLS

Диагноз подтверждён по факту, не по конвенции: наш vhost стоит `default_server` и на 80, и на 443, а имени `xn--80abgfrd5cf.xn--80adkdyec4j.xn--p1ai` не было ни в одном включённом `server_name` (смотрел `nginx -T`, а не `grep -r` по `sites-enabled` — тот молчит, потому что там симлинки, нужен `-R`; на этом я потерял один заход).

Сделано по вашему более дешёвому варианту, владелец выбрал его явно 11.09: **отдельный vhost на :80 с `return 301 https://вмалмыже.рф$request_uri`**, никакого сертификата и никакой новой certbot-линии. `default_server` не трогал — в конфиге соседа есть комментарий, что его ACME-челлендж для неперечисленного имени рассчитывает на дефолтный сервер на :80, и я не хочу это ломать походя.

Приёмка снаружи, через публичный DNS, тремя путями: `/`, `/kakoi-to/put?x=1`, `/brigadir` → все `301` на портал с сохранённым путём и query. Контроль-негатив: `гоньба.рф` → `200`; портал и сосед по :80 отвечают как прежде (`301` на свой https). `nginx -t` чист, `reload`, мастер-процесс не перезапускался.

Цена, как вы и написали: кто придёт по `https://бригадир…` напрямую, по-прежнему увидит предупреждение о сертификате и за ним — нас. Для имени без содержимого это принято.

## 3. Грабля замера, возможно на класс

Первая проверка сразу после `systemctl reload nginx` показала **`301` на `https://бригадир…`**, то есть ответ дефолтного блока (`$host`), а не нашего. Я успел решить, что запись не сматчилась. Через несколько секунд тот же запрос дал верный `Location` на портал.

Механизм: `reload` поднимает новые воркеры и даёт старым доработать; запрос в ту же секунду ушёл в старый воркер со старой конфигурацией. `nginx -t` при этом честно говорил «ok», и `-T` показывал новый блок — то есть **проверка конфигурации и проверка поведения давали разный ответ, и обе были правдой**. Похоже на ваш #252 с другой стороны: не «прибор отказал», а «прибор измерил прошлое». Правило, которое я себе записал: после `reload` приёмку снимать не той же командой, а следующим шагом, и не по одному запросу.
