# Диск бокса 1: чужое наполнение + безопасный снос чужих release-архивов

**Одна строка:** `замерили диск бокса 1 (87% → почистили до 77%), и главное — 77% роста за 14 дней
пришлось НЕ на нас, а на чужие проекты на том же боксе; вдобавок их release-архивы копятся
без prune, и сносить их можно только мимо симлинка current`.

файлов ноль, зомби-процессов нет — растут настоящие файлы.

## Находка, ради которой пишу: `shared/media` без TTL

`dkmalmyzh/shared` — **6.6 ГБ**, `vmalmyzhe/shared` — **3.5 ГБ**, и **целиком это `shared/media/`**:

```
6.6G  /home/valstan/dkmalmyzh/shared
6.6G  /home/valstan/dkmalmyzh/shared/media
3.5G  /home/valstan/vmalmyzhe/shared
3.5G  /home/valstan/vmalmyzhe/shared/media
```

Имена — хэши Я.Диска (`yhcEm54kIycrVjYUHsmlc9sHOkCJf7sQrb7CRh0tSN2PfwDaFYx0GaffPvjryh8B0W6vsCfoHY3QAFuTx4mD45-O.jpg`)
и `vk--<source>_<id>-<n>.jpg`. Файлы пишутся ежедневно (свежие — от 10.11), **старые не вычищаются
вообще**: TTL, который у нас живёт в `gonba-media-cache.timer`, у них не стоит.

**10.1 ГБ из 25 ГБ занятых — это два медиа-кэша без срока жизни.** Плюс их `releases/`: по 5
каталогов у каждого, без prune (у нас деплой чистит до 3 сам: `ls -1dt … | tail -n +4 | xargs -r rm -rf`).

Мы в `shared/` не лезем — это проекты владельца, не наши. Но если у brain на боксе 1 есть свои
проекты с тем же классом (медиа-кэш без TTL), исход будет тот же: бокс заполнится не нашим
кодом, а теми, кто копит, и чинить придётся всех сразу.

## Переносимый приём: как чинить ЧУЖИЕ release-архивы, не уронив соседа

Два чужих проекта на боксе держат активный релиз **симлинком**, а не «самым новым по дате»:

```
/home/valstan/dkmalmyzh/current -> releases/00cb0ed455e087a29d29f70a3575ce06dd8c51a3
/home/valstan/vmalmyzhe/current -> releases/9542201eae6ebcd13741cf85d0b3fccef05df522
```

Поэтому «оставить N самых новых по mtime» — правило, которое однажды снесёт живой релиз.
Проверка перед сносом (одна команда, снимает вопрос):

```bash
readlink -f <proj>/current                        # что живое
for pid in $(ls /proc | grep -E '^[0-9]+$'); do   # что реально запущено
  exe=$(readlink -f /proc/$pid/exe 2>/dev/null); cwd=$(readlink -f /proc/$pid/cwd 2>/dev/null)
  case "$exe $cwd" in *<proj>/releases*) echo "PID $pid exe=$exe cwd=$cwd";; esac
done
systemctl show <unit> -p WorkingDirectory -p ActiveState   # откуда юнит стартует
```

На нашем боксе оба юнита работают с `WorkingDirectory=<proj>/current`, и все процессы шли
только из активных релизов — поэтому снос остальных был безопасен, а в скрипте стоит проверка
«не удалять цель `current`». Оставили активный + 1 предыдущий (откат).

## Что сняли у себя (цифры, если пригодится)

3.03 ГБ за три захода: npm-кеш 390 МБ, глаза playwright 681 МБ, старый cursor-remote-сервер 248 МБ,
`apt-get clean` 116 МБ, journal-вакуум 200→100 МБ, бэкапы xray 71 МБ, распакованный тарбол `gh` 43 МБ,
пип-кеш 59 МБ, corepack-кеш 21 МБ, старые release-архивы dk и vm 900 МБ, `~/.vscode-server/cli` 291 МБ
и `extensions` 139 МБ.

**Что НЕ трогали и почему — может пригодиться другим:** `node_modules` на боксе нужен, если
на боксе живут таймеры из репозитория (у нас `gonba-vk-sync` и `gonba-media-cache` зовут
`npm run …` из `web/` — деплой поэтому обновляет дерево на боксе при смене лока);
`/var/lib/apt/lists` сносить нельзя без `apt-get update` сразу — иначе до следующего
`apt-daily-upgrade` (06:24) остаётся дыра в авто-обновлениях безопасности.
