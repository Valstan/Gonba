# `next` 16.3.8 на проде — peer-долг L-1 закрыт

**Ответ одной строкой:** «поставил next **16.3.8**, приёмка: **SVG через оптимизатор → 400** (вектор закрыт), raster через тот же оптимизатор → **200 `image/png`**, контроль-негатив — тот же SVG напрямую без оптимизатора → **200 `image/svg+xml`**; в задеплоенном артефакте на боксе `node_modules/next` **16.3.8**, `sharp` **0.35.5**; прод `55c84f3`, деплой зелёный, консоль браузера чистая, гидратация живая».

## Что сделано

- **Peer-диапазон сверен командой, а не по памяти** (твой пункт 2 канона G345):
  `npm view @payloadcms/next@3.90.1 peerDependencies.next` →
  `>=15.2.9 <15.3.0 || >=15.3.9 <15.4.0 || >=15.4.11 <15.5.0 || >=16.3.3 <17.0.0`.
  Ветки 15.5 в нём нет — значит 15.5.28 закрывал CVE, но peer-долг не трогал. 16.3.8 — последняя в чистой ветке.
- **Лок пересобран npm 11** (тем же, которым написан): **34 аннотации `"libc"` на месте**, тихой порчи нет (G590 не сработал — сработал бы на npm 10).
- `react` **19.2.1** не тронут, `sharp` **0.35.5** не тронут — пол-апгрейд не тащили, как ты и просил.

## Про гейт на peer — отдельной строкой, как ты и просил

«Обновили» и «peer-долг закрыт» — два разных факта, и **npm их не различает**: в `web/.npmrc` стоит `legacy-peer-deps=true`, поэтому peer-диапазоны не проверяются вовсе, и `npm ls next` показывает «ok» даже на несовместимой комбинации. Поэтому проверка стала **машинной**: `web/scripts/check-next-peer.mjs` читает peer-диапазон из `node_modules` и сверяет его с реально установленной версией — мимо npm; шаг стоит в `ci.yml` **до** сборки.

**Гейт проверяет сам себя** (self-test на эталонных случаях, включая «next 15.5.28 вне диапазона»): гейт, который всегда зелёный или всегда красный, не проверяет ничего. Проверен и в обе стороны вручную — на 16.3.8 зелёный, на 15.5.28 красный.

## Что НЕ сделано — и почему это правильно

**Turbopack-миграцию не делал.** В Next 16 Turbopack — дефолт для `next build` и `next dev`, и **кастомный webpack-конфиг при Turbopack роняет сборку** (так прямо в апгрейд-гайде Next). У нас он есть (`resolve.extensionAlias` — без него Payload-импорты не резолвятся). Поэтому `--webpack` и в `build:raw`, и в `dev`: бандлер и раскладка чанков не меняются вместе с версией. Миграция на Turbopack — это отдельная задача со своим окном и своей приёмкой, а не побочка апгрейда. Твой пункт 3 («не тяни за собой пол-апгрейд без нужды») мы выполнили буквально.

**Пять правил `react-hooks` v7 понизил до warning.** Они приехали с `eslint-config-next` 16 и дали **27 ошибок в 22 компонентах** (`set-state-in-effect` ×20, `purity` ×3, `refs` ×2, `immutability`, `preserve-manual-memoization`). React Compiler у нас не включён — правила advisory; переписывание 22 компонентов это другой объём и другой риск, чем «разрешение на апгрейд версии, а не на любые изменения». Долг заведён в бэклоге с перечнем файлов. Одно новое правило v16 (`@next/next/no-location-assign-relative-destination`, 2 warning'а в админке Payload) оставлено как warning осознанно: там полная перезагрузка осмысленна.

## Находки в пул — переносимое (G<новый>)

1. **Next 16 + кастомный `webpack`-конфиг = падение сборки.** Не деградация, а ошибка: Next 16 останавливает сборку, чтобы не собрать не то. Обход — `--webpack`, и это дефолтный путь для проектов с webpack-конфигом.
2. **`eslint-config-next` 16 отдаёт flat-конфиг, и `FlatCompat` на нём падает** с «Converting circular structure to JSON» — то есть не «конфиг устарел», а **линт не запускается вообще**. Лечение: `import nextCoreWebVitals from 'eslint-config-next/core-web-vitals'` + `nextTypeScript` напрямую, без `FlatCompat`.
3. **Flat-конфиг требует плагин в том же объекте, где применяются его правила.** Иначе «plugin is not defined within the same configuration object». Если импортируешь плагин сам — делай его **прямой** зависимостью, а не транзитивной.
4. **Next 16 требует `jsx: "react-jsx"` в tsconfig** («next.js uses the React automatic runtime») и **переписывает tsconfig сам** — то есть версию надо закоммитить, иначе сборка перепишет конфиг заново. Заодно Next 16 дописывает в `next-env.d.ts` `import "./.next/types/routes.d.ts"` — файл генерируемый, в коммит его брать нельзя (у нас он и не берётся, `skipLibCheck` спасает `tsc` в CI).
5. **`legacy-peer-deps=true` прячет peer-конфликты от `npm ls`** — если у проекта есть такой флаг, «зелёный» peer-статус ничего не значит. Лечение — гейт, читающий диапазон из `node_modules` напрямую.
6. **Windows-ловушка нашего репо (не про Next):** `npm run build` и `npm run test:int` на Windows не работают — `run-with-watchdog.mjs` делает `spawn npm` без shell, а на Windows npm это `npm.cmd` → ENOENT. Рабочий путь локально — `build:raw` / `test:int:raw`. Это давно, не связано с апгрейдом, лечится двумя строками.
